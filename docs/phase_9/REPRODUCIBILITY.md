# Phase 9 — Reproducibility

How to install the tested environment, verify the published bundle, run the project, and, separately, how the bundle was produced. Measured results in this page come from `artifacts/med-deploy-v1/` and are generated by `python -m med_deploy report`.

## Runtime and pins

- **Python 3.11.14** is the tested interpreter (`.python-version`; the images and CI use it). `pyproject.toml` still says `requires-python = ">=3.11"`, so the core install stays light and works on other 3.11 and later interpreters; only 3.11.14 is the tested one.
- **`constraints.txt`** pins every third-party package of the core install and of the `dev`, `ui`, and `monitor` extras, exactly as tested. It pins third-party packages only, never this project: a raw `pip freeze` would add an editable install of the project pinned to one commit and is not portable. A constraints file installs nothing by itself: `pip install -c constraints.txt .` takes only what the core needs, so the API image does not get Streamlit or pyarrow even though both are pinned.
- **Build backend.** The project builds with setuptools from `pyproject.toml`; the build tool is fetched at install time and is not pinned, which affects how this project's own wheel is built, not which third-party versions run.
- **Platform-conditional packages.** A freeze made on one platform lacks what another installs: Streamlit needs `watchdog` on Linux but not on macOS. The first Linux image build installed `watchdog` unpinned, which the image check reported, and it is now pinned; a test evaluates the dependency markers of the installed packages for macOS and Linux so a missing pin is caught.
- **No new locking tool** was added. To regenerate the pins after a deliberate upgrade, run the tests in an environment built from the new versions and compare `python -m med_deploy environment --freeze` from each platform you support (the Linux images report `environment --constraints constraints.txt` the same way).

## Fresh checkout

```bash
python3.11 -m venv .venv            # use Python 3.11.14 to match the tested environment
source .venv/bin/activate
pip install -c constraints.txt -e ".[dev,ui,monitor]"
pip check
python -m med_deploy environment --constraints constraints.txt --check   # exits 1 on any difference from the pins
python -m med_deploy check-bundle --scope api                            # artifact versions and checksums, no scoring
python -m med_deploy check-bundle --scope ui
python -m pytest -m "not slow" -q                                        # the CI selection
python -m med_deploy smoke --spawn                                       # API process plus the review screen, end to end
```

Release gate (about nine minutes, not run in CI): `python -m pytest` and `python -m med_data validate --data data/med-synth-v4`.

Start the services without containers, in two virtual environments if you want the API to keep its faster Python string storage (see below):

```bash
python -m med_api serve                # http://127.0.0.1:8000, bundle verified at startup
python -m med_ui                       # http://127.0.0.1:8501 (loopback by default; --host to change)
```

## Why the API is kept apart from pyarrow

Streamlit requires pyarrow. When pyarrow is importable, pandas 3 stores strings in Arrow by default. Every result is unchanged, but the data and feature pipeline runs about three times slower (`python -m med_data validate` took 159.8 s with pyarrow against 49.1 s without, in Phase 7). **Decision: split environments, do not pin pandas in the packages.** The scoring API image installs the core package only, so pyarrow is not importable in it; the review screen, which never scores, has its own image with pyarrow. `tests/conftest.py` pins pandas to Python string storage for the test suite. The measured images above record whether pyarrow is importable in each. `python -m med_deploy environment` reports it for any environment, and the latency record states it for the measured process.

## The published bundle, and how it was produced

**Using the published frozen bundle** (what a person running the demo does): the dataset `med-synth-v4`, features `med-features-v2`, model `med-model-v2`, and policy `med-policy-v2` are in the repository with checksums. Nothing is regenerated, refit, or re-evaluated to install or serve them. `check-bundle` verifies them; the API verifies them again at startup and refuses to serve a mismatch.

**Rebuilding** is a separate procedure, not part of installing, an image build, or CI. The frozen test subsets of `med-synth-v4` were evaluated once for `med-policy-v2`; a new policy needs a new version and a new frozen dataset version. The data build refuses to write into a directory that already holds a dataset. The feature and model commands do **not** refuse to overwrite their default output directories, and `med_models run` also rewrites `docs/phase_4` and trains on the published features by default, so **never run `python -m med_features build` or `python -m med_models run` with default paths**. A rebuild demonstration sends every output to a scratch directory and trains on the scratch features:

```bash
SCRATCH="$(mktemp -d)"
python -m med_data build --output "$SCRATCH/data"        # into a new directory; compare dataset_manifest.json with the published one
python -m med_features build --output "$SCRATCH/features"
python -m med_models run --features "$SCRATCH/features" --output "$SCRATCH/model" --docs "$SCRATCH/docs"
```

The threshold step (`python -m med_policy select`) and the frozen evaluation (`python -m med_policy evaluate-test`) are one-shot commands and are not part of any rebuild demonstration. `python -m med_api latency` is the one-shot Phase 6 measurement; Phase 9 measures latency with `python -m med_deploy latency`, which writes a new record.
