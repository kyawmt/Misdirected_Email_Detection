# Phase 9 — Rollback rehearsal

Generated by `python -m med_deploy report` from `artifacts/med-deploy-v1/rollback_rehearsal_*.json`. The rehearsal is a **local** exercise: a known-good deployable and a failing candidate, swapped on one machine. It is not a live hot swap, a canary, or a shadow router; none of those exists. It follows the rollback steps in [the runbook](../phase_8/RUNBOOK.md) and does not change them.

## How the rehearsal works

- **Known-good** is a code-plus-bundle deployable with a content-addressed identity that is never edited: an image id for containers, the SHA-256 of the policy, model, and feature manifest for processes.
- **A candidate** is the known-good deployable with one injected fault: a flipped byte in `model.joblib` (the policy records the model's SHA-256), or `policy.json` removed. For containers a candidate is a thin image layered on the known-good image; for processes it is a disposable copy. No published or frozen file is edited in place.
- **Verification** of a healthy deployable: `/health`, `/ready` with the versions and `T_warn` of the policy file, every scenario fixture (including an allow, a warning, and the known misses), and one reviewed-label click that must add exactly one line (no address) to the rehearsal's own feedback file, change no decision, and change no bundle file. In the container rehearsal the review screen container must also be healthy and must see `/ready` 200 from inside its own network.
- **Verification of a failing candidate:** the process is up, `/ready` is 503 with a reason, `/assess` is `unable_to_assess` with no decision, no score, and no versions, the scenario suite flags every assessed fixture, the health command a container runs fails, and nothing is written to the feedback file. The review screen script, run headlessly on the host against the failing API, must disable assessment and say the service is not ready. In the container rehearsal the review screen container must stay healthy and must see `/ready` 503 from inside its own network; a container that is unreachable or unhealthy at any step fails that step.
- **Restore:** the known-good deployable is started again and everything above is re-verified.

## Commands

The published records under `artifacts/med-deploy-v1/` are the outputs of the run described above and are write-once: a command that names one of them is refused. To rehearse again, write to a scratch path (the commands below can be run as printed; `<scratch>` is any directory you can write to, for example `mktemp -d`):

```bash
docker/build.sh                                  # build med-api:phase9 and med-ui:phase9
python -m med_deploy images --record <scratch>/images.json
python -m med_deploy rehearse --mode container --record <scratch>/rehearsal_container.json
python -m med_deploy rehearse --mode process   --record <scratch>/rehearsal_process.json
```

To roll back the running demo by hand, point compose at the known-good image id and recreate only the API: `MED_API_IMAGE=<known-good image id> docker compose up -d --no-build --force-recreate --no-deps api`, then check `GET /ready`, run `python -m med_deploy regress --api http://127.0.0.1:8000`, and confirm the container's image id with `docker inspect`. Do not edit a bundle inside a running container; a new bundle is a new image.

## What this does not cover

- A live switch between two loadable bundles, a shadow mode that records a decision without showing it, and a per-sender routing switch are **future capabilities**; none was built.
- The previous bundle (`med-policy-v1`) is refused by the current code by design, so it cannot be a rollback target; a rollback needs the previous code and its bundle as a pair, which is what a known-good image is.
- A candidate here is the known-good bundle with a fault. The rehearsal shows that a broken bundle fails closed and that the known-good deployable restores and verifies; it does not show that a different, healthy model can be promoted. Promotion still needs the gates in [the runbook](../phase_8/RUNBOOK.md).
